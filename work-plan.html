The source-watch baseline

A fingerprint baseline is the record of what each cited page looked like the first time we checked it. Until it exists, change detection has nothing to compare against. This is the one deliverable the authoring environment cannot produce by itself.

Why the runner had to create it, not this environment

  • The shell has no outbound network. Re-confirmed this session: requests to the registered hosts fail at the TLS handshake, so node tools/check-sources.mjs --dry-run reports every URL unreachable. That is an environment limitation, not evidence that the pages are dead — the same pages were read through the research tools during this session.
  • This session's GitHub token cannot dispatch workflows. gh workflow run returns HTTP 403 “Resource not accessible by integration”, so the baseline could not be triggered from here either. The fix was to stop depending on a dispatch: the workflow itself now runs when a push to main happens and no baseline exists.

How the baseline gets created, and what proves it will work

  • Scheduled: the Action runs every Monday at 07:00 UTC and always runs on main.
  • By hand: a maintainer with the repository's own token can run gh workflow run source-watch.yml --ref main -f init=true, or use “Run workflow” in the Actions tab with Baseline only ticked.
  • Automatically: a preflight job lets the workflow run on a push to main only when tools/source-state.json is missing. So a baseline that is lost — or never created, as here — repairs itself on the next push to main, and ordinary pushes never pay for a network run.
  • The watcher's behaviour is now machine-tested offline (tools/test-source-watch.mjs): a first run writes a baseline and files no issue; an edited page is reported; a previously reachable page that stops responding is reported as a regression and keeps its old fingerprint; a runner that can reach nothing writes no baseline at all and fails the job loudly, so a broken runner cannot silently become an empty “baseline” that later runs compare against.

What the first run will do. It records every reachable source as newly baselined (no issue is filed for that), commits tools/source-state.json, and prints a step summary with the counts. If it reports zero reachable sources, the job fails on purpose: that means the runner itself is blocked and the citations need another route, not that the whole citation set is dead.

Status on this snapshot: Established — the first run completed on 19 September 2026 at 00:20 UTC and committed tools/source-state.json with 86 of 87 URLs fingerprinted. The one source it could not reach was the Sportskeeda interview (HTTP 403); under the two-strike rule that is recorded as a first failure, not as a dead page, and the next scheduled run — Monday 21 September 2026, 07:00 UTC — decides whether it becomes a real regression (Wowhead's summary of the same interview wh-sportskeeda is the Wowhead URL and is fine). Re-checked in the later session: the committed tools/source-state.json still shows 86 hashed entries and one first failure, and no second run had happened yet. Among the sources fingerprinted on the first pass were the Blizzard newsroom and forum pages, Wowhead, Icy Veins, Kotaku, Skill Capped, Wago and CurseForge — the pages the ledger actually cites.

That boundary is what makes automation compatible with a no-hallucination rule, and this session widened the automation without crossing it.
